# 8 · One rule, one place (and a test that never sleeps)

**The idea.** Last interview move: a rule changes. The bank now allows an
**overdraft**: `Bank(overdraft=100)` lets a balance go down to -100.
Count how many places in your code decide "can this account pay?".
Withdraw, transfer, scheduled payments, and now merge. If each has its own
`<` check you must find and fix all of them, and the one you miss is the
bug. The refactor: one helper that holds the rule, called from everywhere.

```python
class Gym:
    def __init__(self, max_people=30):
        self.max_people = max_people
        self.inside = 0

    def _has_room(self, n):                 # the ONE place with the rule
        return self.inside + n <= self.max_people

    def enter(self, n):
        if not self._has_room(n):
            return None
        self.inside += n
        return self.inside
```

The second idea is how interviewers test code like this: an **invariant**,
a fact that must be true after every single operation. For a bank:
money never appears or vanishes. They run thousands of random operations
(with a fixed seed, so the run is the same every time) and check the
invariants after each one. A test like that finds bugs nobody thought of.

**Your turn.**
- `Bank(overdraft=0)`: a whole number, 0 or more, else `ValueError`.
  `Bank()` must behave exactly as before.
- withdraw, transfer and scheduled payments may take a balance down to
  `-overdraft`, never below
- `merge_accounts` returns `False` if the merged balance would be below
  `-overdraft`

**Checked:** the limit is exact everywhere, then 1500 seeded random
operations: no balance below the limit, history always adds up to the
balance, top_spenders always sorted, and no cent is ever lost.
