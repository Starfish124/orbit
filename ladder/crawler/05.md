# 5 · Eight at once (threads)

**The idea.** Fetching a page is mostly *waiting* for the network. One by
one, 20 pages at 0.03 s each take 0.6 s of waiting. **Threads** let several
waits overlap. `ThreadPoolExecutor` runs a function on many inputs with a
fixed number of worker threads, and `map` hands back results in input order:

```python
import time
from concurrent.futures import ThreadPoolExecutor

def bake(cake):
    time.sleep(0.1)              # the "waiting" part
    return cake + " done"

with ThreadPoolExecutor(max_workers=4) as pool:
    print(list(pool.map(bake, ["a", "b", "c", "d"])))   # ~0.1 s, not 0.4 s
```

The catch: threads run *at the same time*. If two threads both do
`if url not in seen: seen.add(url)`, both can check before either adds,
and the page gets fetched twice. Two cures:

- a `threading.Lock()`: `with lock:` lets one thread at a time through
  the check-and-add
- simpler: let workers **only fetch**. The main thread hands out one BFS
  level at a time, collects the results, and is the only one that ever
  touches `seen`. No sharing, no lock needed.

**Your turn.** `crawl_threaded(start, fetch, workers=8)`:
- returns the same set `crawl(start, fetch)` would (normalized, same host,
  failed pages don't crash it)
- at most `workers` fetches at the same time
- every page fetched exactly once

**Checked:** same result as `crawl` on the messy site; 20 slow pages in
under 0.3 s with 8 workers; `workers=1` never runs two fetches at once.
