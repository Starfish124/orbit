# 8 · A budget and a stopwatch

**The idea.** Two last follow-ups every crawler interview reaches.

**A budget.** "Fetch at most 100 pages." The lazy fix is to count after
fetching, but by then you have already hit the server. Better: never
*start* work you won't keep. Before each level, cut it down to what the
budget has left; a slice past the end is just shorter, never an error:

```python
queue = ["a", "b", "c", "d"]
left = 2
print(queue[:left], queue[:10], queue[:0])   # ['a', 'b'] [...all 4] []
```

**A stopwatch.** One page that never answers would freeze your whole
crawl. `asyncio.wait_for(coro, seconds)` waits at most that long; then it
**cancels** the coroutine (stops it at its current `await`) and raises
`TimeoutError`, an ordinary exception you already know how to catch.
`wait_for(coro, None)` waits forever, so it can sit there always.

```python
import asyncio

async def main():
    try:
        await asyncio.wait_for(asyncio.sleep(60), 0.1)
    except TimeoutError:
        print("gave up after 0.1 s")

asyncio.run(main())
```

**Your turn.** `crawl_async(start, fetch, limit=None, max_pages=None, timeout=None)`:
- `max_pages`: call `fetch` at most that many times, in BFS order (first
  levels first, links in the order they appeared)
- the result is now **the pages you fetched** (tried). Without a budget
  that is everything you found, so nothing changes there
- `timeout`: a fetch slower than that is cancelled and treated as failed

**Checked:** budgets 1, 4 and 5 give exactly the first pages in level
order; a 3-second page with `timeout=0.05` is cancelled and the crawl
still finishes fast.
