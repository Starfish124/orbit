# 8 · Peek and resize: the last follow-ups

**The idea.** Two classic "one more thing" requirements:

- **peek**: look at a value *without* counting as a use. Debug tools and
  monitoring must not change what gets evicted. A read that has no side
  effects is a different operation from `get`, even if it returns the same.
- **resize**: memory is tight, shrink the cache now. Evict least recently
  used keys until it fits, and each eviction is a normal one (callback,
  counter). Growing just raises the limit.

Reuse, don't copy: if eviction code now lives in two places, pull it into
one helper method (a name starting with `_` says "internal").

**Your turn.**
- `peek(key)`: value or `None`; changes neither recency nor stats
- `resize(capacity)`: below 1 → `ValueError`; shrinking evicts LRU-first
  through the same path as `put` (callback + evictions counter)

**Checked:** peek leaves order and stats alone; resize(1) from 3 keys
evicts two, in LRU order, through on_evict; growing then holds more.
