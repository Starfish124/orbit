# 7 · Measure retrieval before you tune it

**The idea.** Chunk size, k1, b, min_score: every knob changes results, and
eyeballing one query tells you nothing. Real teams build a small **labeled
set** (questions with the chunk ids that answer them) and score retrieval
with numbers. Change a knob, rerun, compare. No number, no tuning.

- **recall@k**: of the relevant ids, what fraction appear in the top `k`?
  "Did the answer make it into the prompt at all?"
- **reciprocal rank**: 1 / position of the *first* relevant hit (positions
  start at 1), 0 if none. **MRR** is its mean over the questions. "How
  high up was it?"

`enumerate(items, 1)` counts from 1 instead of 0. Different job, the first
passing student in a ranked exam list:

```python
ranked = ["ana", "ben", "cy"]
passed = {"ben", "cy"}
for pos, name in enumerate(ranked, 1):
    if name in passed:
        print(pos, 1 / pos)      # 2 0.5
        break
```

**Your turn.**
- `recall_at_k(ranked, relevant, k)`: `ranked` is a list of ids, `relevant`
  a set; the fraction of `relevant` found in `ranked[:k]`
- `reciprocal_rank(ranked, relevant)`: as above, `0.0` when none
- `evaluate(search, labeled, k)`: `labeled` is a list of
  `(question, relevant_set)`; for each, call `search(question, k)` (it
  returns `(id, score)` pairs, like `Index.search`) and score the ids.
  Return `{"recall": mean recall@k, "mrr": mean reciprocal rank}`. An empty
  `labeled`: `ValueError`.

**Checked:** exact values on hand-made rankings, one call per question, and
a real `Index.search` passed in as the search function.
