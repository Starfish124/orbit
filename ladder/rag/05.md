# 5 · An Index you can keep adding to

**The idea.** Wrap the pieces in a class that owns the chunks. Two design
points an interviewer will push on:

1. **Statistics are global.** BM25 needs `N`, `df` and `avgdl` over *all*
   chunks. If you compute them once when documents are added and cache
   them, the next `add_documents` makes them stale and every score after
   is quietly wrong. Keep the raw material (each chunk's tokens) and
   compute scores from it at search time. Correct first; fast later.
2. **Validate before you change anything.** If a call fails halfway, the
   index must be as it was. Check every input first, then write.

Same shape, different job: a class that adds all or nothing.

```python
class Roster:
    def __init__(self):
        self.names = set()

    def enrol(self, new_names):
        for n in new_names:                  # check everything first
            if n in self.names:
                raise ValueError("already enrolled: " + n)
        for n in new_names:                  # only then change state
            self.names.add(n)
```

**Your turn.** `class Index`:
- `Index(size=100, overlap=20)` stores the chunking settings
- `add_documents(docs)`: `docs` is `{doc_id: text}`; chunk each with your
  `chunk`, remember each chunk's text and tokens. A `doc_id` already in the
  index: `ValueError`, and nothing from that call is added
- `text(chunk_id)` returns that chunk's text
- `search(query, k=3)`: `top_k` of `bm25(tokenize(query), {chunk_id: tokens})`
  over every chunk

**Checked:** chunk texts, search order, k default, no-match, incremental adds
score exactly like one big add, duplicate ids rejected without side effects.
