# 4 · A model as the grader

**The idea.** "Summarise this email" has no single right string. Teams
use *LLM-as-judge*: a second model gets a rubric prompt and answers PASS
or FAIL. The judge is also a model, so it can ramble, use markdown, or
answer something unreadable. The rule: **an unreadable verdict is never a
pass.** It goes in its own `judge_error` bucket so you can see how often
your judge is broken, instead of silently counting noise as wins.

A function can build and return another function. The inner one remembers
the variables around it (a *closure*). That's how you turn "a judge" into
"a grader" with the same `(output, expected)` shape `run` already takes:

```python
def make_greeter(greeting):
    def greet(name):
        return greeting + ", " + name      # remembers greeting
    return greet

hi = make_greeter("Hi")
print(hi("Ana"))    # Hi, Ana
```

**Your turn.**
- `judge_prompt(output, expected)`: a prompt string containing the answer,
  the reference and the words `PASS` and `FAIL`
- `parse_verdict(text)` → `(verdict, reason)`. Take the first non-blank
  line, strip spaces, `*` and `#` from its ends. If its first 4 letters are
  `PASS` or `FAIL` (any case), verdict is `"pass"`/`"fail"` and reason is
  the rest of that line (strip `*:-.,` and spaces) plus the remaining
  lines, joined by single spaces. Anything else → `("judge_error", why)`.
- `llm_judge(judge)` returns a grader that calls `judge(prompt)` once. Pass
  → `(True, reason)`, fail → `(False, reason)`; unreadable reply *or* a
  judge that raises → `(False, "judge_error: ...")`
- `run` gains a `"status"` per result: `"pass"`, `"fail"`, `"error"`
  (system raised) or `"judge_error"` (reason starts with `judge_error`),
  and a `"counts"` dict with all four statuses

with a flaky judge gives statuses pass, fail, judge_error, judge_error.
