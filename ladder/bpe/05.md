# 5 · Encode and decode: a real tokenizer

**The idea.** The merges are the tokenizer's rulebook. To **encode** new
text: get its bytes, then apply each merge *in the order it was learned*
(dicts keep that order). To **decode**: look up what bytes each id stands
for and glue them. That lookup table is the **vocab**: `{id: bytes}`.
Ids 0..255 are single bytes, `bytes([97])` is `b"a"`. Every merged id is
its two halves joined: `vocab[a] + vocab[b]`. Build it in merge order and
both halves already exist.

`bytes` join with `+` like strings. One trap: an id list can cut a
character in half (`[195]` is half of `"é"`), and `.decode("utf-8")` then
crashes. `.decode("utf-8", errors="replace")` puts `"�"` there instead.

```python
parts = {0: b"caf", 1: b"\xc3", 2: b"\xa9"}
glued = parts[0] + parts[1] + parts[2]
print(glued.decode("utf-8"))                    # café
print(parts[1].decode("utf-8", errors="replace"))   # �
```

**Your turn.** `class Tokenizer`, keeping all the functions from before:
- `Tokenizer()`: `self.merges = {}` and `self.vocab` holding ids 0..255
- `train(text, vocab_size)`: uses your `train` function, then rebuilds `vocab`
- `encode(text)` -> list of ids, `decode(ids)` -> `str`

**Checked:** after training on `"aaabdaaabac"`, `vocab[258] == b"aaab"`,
encode gives `[258, 100, 258, 97, 99]`, round trips on accents and emoji,
`decode([195])` is `"�"`.
